# Copy Trading Dashboard — v1 fix pass (v2)

The six issues from the v1 review have all been addressed: credentials are stripped from API responses via a `redactAccountCredentials` helper, the copy engine now has a webhook-based runtime trigger (`POST /api/groups/[id]/webhook`), the `accountId`→`tradingAccountId` field mismatch is fixed in both group routes, settings persist through a `UserPreferences` model and `/api/settings` API, and NinjaTrader/Rithmic are disabled in the UI with "Coming Soon" badges and return a 400 from the sync route.

**Watch for:** The daily-loss circuit breaker is permanently inert — `dailyLossUsed` is hardcoded to 0 on every webhook call, so the risk limit can never fire (confirmed). The webhook creates a fresh `TradovateAdapter` per request but never calls `connect()` before `placeTrade`, so follower trades will fail at runtime (confirmed). Credential fields are still stored as plaintext in the database — redaction from responses is good, but at-rest exposure remains (likely, same as v1 but now defense-in-depth only).

**Verdict**: NEEDS_CHANGES

## High-level view

The credential redaction strips `apiKey`/`apiSecret` at the serialization boundary across all response sites (list, get, create, update, sync), removing them entirely rather than masking — the safest approach for an API surface.

The webhook endpoint provides the missing runtime activation path for the copy engine, but the adapter lifecycle inside it is broken. Each request instantiates a new `TradovateAdapter` via `getAdapter` but never calls `connect()` before the engine calls `placeTrade`. The adapter's internal state (auth token, session) won't be initialized, so every follower trade will fail.

The daily-loss gating — one of the engine's core safety features — is dead code in the webhook path because `dailyLossUsed` is always set to `0` when building the `groupConfig`. Under high-frequency signals, a follower account has no circuit breaker.

The webhook requires a NextAuth session, making it unreachable from external signal sources (TradingView alerts, platform callbacks). The `copy-service.ts` module provides a real-time subscription alternative, but for the serverless webhook path, machine authentication is missing.

## Webhook adapter lifecycle gap

The `getAdapter` function inside the webhook route constructs a new adapter on each call but returns it immediately without connecting:

```typescript
const getAdapter = (accountId: string) => {
  const memberEntry = group.members.find(
    (m) => m.tradingAccountId === accountId
  );
  // ...
  const adapter = createPlatformAdapter(platform);
  // Note: In production, adapters would be pre-connected.
  return adapter;
};
```

The `TradovateAdapter.placeTrade` relies on an authenticated HTTP session established by `connect()`. Without it, every trade placement hits an unauthenticated API call. The webhook will return a 200 with individual `success: false` results for each member — a fail-open pattern at the HTTP level that masks a total failure at the trade level.

Contrast with `copy-service.ts`, which correctly calls `adapter.connect(member.credentials)` for each follower — but `copy-service.ts` is not used by the webhook route. The two implementations solve the same problem differently and only one is wired up.

## Daily-loss calculation gap

The copy engine's `checkRiskLimits` compares `member.dailyLossUsed` against `member.maxDailyLoss`:

```typescript
if (member.dailyLossUsed >= member.maxDailyLoss) {
  return { allowed: false, reason: `Daily loss limit reached...` };
}
```

The webhook handler builds the config with:

```typescript
members: group.members.map((member) => ({
  // ...
  dailyLossUsed: 0, // Could be computed from daily metrics
})),
```

The `DailyMetric` model exists with `realizedPnl` and the `Trade` model has `pnl` per trade — either could back this calculation. Neither is queried. Every webhook invocation sees every member as having zero loss for the day, so the circuit breaker cannot engage regardless of actual P&L. This is a safety-critical gap: the feature's purpose is to prevent runaway losses.

## Webhook authentication model

The webhook is gated by `getServerSession(authOptions)` — standard for browser-originated requests but incompatible with external signal sources. The primary use case for a copy-trading webhook is receiving signals from TradingView alerts, platform callbacks, or automated systems that don't carry a browser session cookie.

For the serverless webhook path, an API key per group (stored hashed, passed in an `Authorization` header) or HMAC signature verification would allow machine callers while maintaining security. Without this, the webhook is only callable from the app's own frontend, limiting it to manual signal submission.
