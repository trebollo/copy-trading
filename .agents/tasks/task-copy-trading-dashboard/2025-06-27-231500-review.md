# Copy Trading Dashboard — Full-stack greenfield build

A Next.js 14 App Router application for managing funded trading accounts across platforms (Tradovate, NinjaTrader, Rithmic), copying trades from master accounts to followers with configurable risk controls, and viewing aggregated performance metrics. The stack is Next.js + Prisma + NextAuth (Google OAuth) + Tailwind/shadcn on the front, with Zod validation and a platform adapter pattern on the backend. The copy engine applies risk multipliers, max-lot caps, and daily-loss limits before forwarding signals.

**Watch for:** API credentials stored in plaintext in the database and returned unredacted in GET responses (confirmed). The copy engine is a pure library with no runtime integration — no WebSocket listener, no event loop, no mechanism that triggers trade copying in production (confirmed). The group creation API writes `accountId` but the Prisma schema expects `tradingAccountId` — this will fail at runtime (confirmed). Settings page is entirely client-side state with no persistence (confirmed).

## High-level view

The platform adapter pattern (`PlatformAdapter` interface + `TradovateAdapter` + factory) provides a clean extension point for new brokers, but only Tradovate has a real implementation. NinjaTrader and Rithmic throw "not yet implemented" errors at sync time, meaning users can create accounts for those platforms in the UI but will hit a hard unhandled failure when they try to use them.

The copy engine (`CopyEngine`) implements risk gating logic — multiplier scaling, lot caps, daily-loss circuit breakers — and is thoroughly unit-tested. However, it has no integration with any event source. The `subscribeTrades` method on the adapter returns an unsubscribe function but nothing in the codebase calls it, connects it to the copy engine, or persists copy results. The entire copy-trading flow exists as testable library code with no production activation path.

API routes follow a consistent pattern: session check, ownership verification, Zod validation, Prisma operation. The authorization model scopes every query to `userId`. But API credentials (`apiKey`, `apiSecret`) are stored as plaintext strings in PostgreSQL with no encryption, and flow through GET response bodies without redaction.

The settings page — notifications, preferences, platform connections — manages state purely in React `useState` hooks with no API calls or backend model. Every preference resets on page reload.

The `CopyGroupMember` Prisma model has a `tradingAccountId` field, but both the group creation route and the add-member route write `accountId` in their `prisma.create` calls. Prisma will reject the unknown field at runtime, making copy group creation broken as shipped.

## Plaintext credentials and missing redaction

The `TradingAccount` model stores `apiKey` and `apiSecret` as nullable `String` columns with no encryption:

```prisma
model TradingAccount {
  apiKey    String?
  apiSecret String?
}
```

The `POST /api/accounts` handler writes them directly from the validated request body. The `GET /api/accounts` handler returns the full Prisma object (including these fields) in the JSON response. The sync route reads them back to pass to the adapter's `connect()`. Any XSS vulnerability or intercepted response leaks plaintext broker credentials.

At minimum, add a Prisma `select` or `omit` on GET routes to exclude secrets, and consider envelope encryption for stored values.

## Copy engine: library without a runtime

The `CopyEngine` class and its `processTradeSignal` method are fully implemented and tested (8 test cases covering inactive groups, inactive members, risk limits, adapter errors, multiple-member fanout). The `TradovateAdapter.subscribeTrades` method accepts a callback and stores it in a `Set`, returning an unsubscribe function.

But no code anywhere:
- Calls `subscribeTrades` on the master adapter
- Connects the callback to `copyEngine.processTradeSignal`
- Persists the resulting `CopyTradeResult` into the `Trade` table with `copiedFromId` set
- Runs a long-lived process or edge function to keep the subscription alive

The toggle endpoint (`POST /api/groups/:id/toggle`) flips `isActive` in the database but nothing reads that flag at runtime to start/stop copying. The product's core value proposition — automated trade copying — has no execution path.

## Group member creation field mismatch

The Prisma schema defines the column as `tradingAccountId`:

```prisma
model CopyGroupMember {
  tradingAccountId String
  tradingAccount TradingAccount @relation(fields: [tradingAccountId], references: [id])
}
```

But the group creation API writes `accountId`:

```typescript
members: {
  create: members.map((member) => ({
    accountId: member.accountId,  // Wrong field name
    riskMultiplier: member.riskMultiplier,
    ...
  })),
}
```

The same mistake in `POST /api/groups/:id/members`:

```typescript
const member = await prisma.copyGroupMember.create({
  data: {
    groupId: id,
    accountId,  // Wrong field name
    ...
  },
});
```

Prisma's generated client will reject `accountId` as an unknown field on `CopyGroupMember`. Fix: change `accountId` to `tradingAccountId` in both routes.

## Settings page is a mockup

All state lives in `useState` hooks with no API calls:

```typescript
const [notifications, setNotifications] = useState<NotificationSettings>({...});
const [preferences, setPreferences] = useState<Preferences>({...});
const [platforms] = useState<PlatformConnection[]>(defaultPlatforms);
```

There is no user preferences model in the Prisma schema, no API route for settings, and no persistence handler. The platform connection list is hardcoded (`defaultPlatforms` with Tradovate always shown as "connected" regardless of actual state).

## Test coverage gaps

Not tested:
- Any API route (no integration/request tests)
- Authentication/authorization flow
- The Tradovate adapter's HTTP interactions (no mock-server tests)
- UI components (despite `@testing-library/react` being installed)
- The actual Prisma queries (the field-name bug above would be caught by a single integration test)

The test pyramid is heavily weighted toward pure-function unit tests. The API layer — where authorization, validation, and database interaction meet — has zero automated coverage, which is why the `accountId`/`tradingAccountId` mismatch shipped undetected.
