# Demo mode gating for client components

This change introduces a `NEXT_PUBLIC_DEMO_MODE` environment variable and an `isDemoMode()` utility so that client components can distinguish between demo mode (show hardcoded sample data) and production mode (start empty, fetch from API). Ten component files were updated to conditionally render mock data or empty states. A Tradovate credentials dialog was added to the settings page for connecting in production mode.

**Watch for:** The server-side `DEMO_MODE` variable and client-side `NEXT_PUBLIC_DEMO_MODE` are independent — setting only the client variable to `false` still causes the `/api/metrics` route to return mock data, which the client then displays as real data (confirmed). The Tradovate authentication endpoint in the settings page uses a different URL casing than the adapter, which will fail on case-sensitive servers (confirmed). The dashboard's Recent Trades section always shows mock trades or nothing — there is no production fetch path for trades (confirmed).

## High-level view

The core mechanism is simple: `isDemoMode()` reads `NEXT_PUBLIC_DEMO_MODE` at the client, and every component branches on it — mock data for demo, empty state plus API fetch for production. The problem is that this only gates the client-side initialization. The `/api/metrics` route still checks the separate server-side `DEMO_MODE` env var and returns mock data if the user has no session or no accounts. When a user sets `NEXT_PUBLIC_DEMO_MODE=false` but leaves `DEMO_MODE=true` (or doesn't set it at all — the `.env.example` default is `true`), the metrics dashboard and dashboard overview will happily render the server's mock data as though it were real. The user's bug report ("I set DEMO_MODE to false and still see fake data") almost certainly comes from this split.

The Tradovate integration in settings makes a direct `fetch` to `demo.tradovateapi.com` from the browser, which will fail due to CORS unless Tradovate explicitly allows the app's origin. The connection flow also silently marks the platform as "connected" on network errors, masking failures.

The trades page and dashboard Recent Trades section have no production fetch logic at all — they show empty state in non-demo mode regardless of whether trade data exists in the database.

1. **Server/client demo mode desync** — The `/api/metrics` route checks `DEMO_MODE` (server), not `NEXT_PUBLIC_DEMO_MODE`. When user sets only the client var to `false`, the API still returns mock metrics which the client renders as real. 3. **CORS block on client-side Tradovate auth** — The settings page calls `demo.tradovateapi.com` directly from the browser. Unless Tradovate's CORS policy allows the app origin, this will fail. The auth request should go through a server-side API route that proxies the call.
4. **Silent success on network error** — `handleTradovateConnect` catches fetch errors and marks the platform as "connected" with a "credentials saved" toast. This means any network failure (CORS, DNS, timeout) looks like success.
5. **No trades fetch in production** — `TradesPageContent` and the dashboard `recentTrades` have no API call in production mode; they always show empty. If trades exist in the database, users will never see them.
6. **Finances localStorage-only persistence** — In production mode, `FinancesPageContent` reads from `localStorage` only. There's no API-backed persistence; clearing browser data loses all transactions.
7. **Two env vars for one concept** — `.env.example` introduces `NEXT_PUBLIC_DEMO_MODE` alongside `DEMO_MODE` without documenting that both must be toggled together. This will confuse every deployment.

## Server-side mock data leaks into production UI

The `/api/metrics` route (not modified in this PR but consumed by it) returns hardcoded mock data under two conditions: (1) no authenticated session when `DEMO_MODE=true`, (2) authenticated user with zero accounts when `DEMO_MODE=true`. The client code in `MetricsDashboard` and `DashboardOverview` only suppresses server data when `totalTrades === 0 && accountCount === 0`. Since the mock payload contains `totalTrades: 142` and `accountCount: 3`, the client's guard fails and it renders fake metrics as production data.

```typescript
// metrics-dashboard.tsx — this guard never fires against the mock payload
if (data.metrics?.totalTrades === 0 && data.accountCount === 0) {
  setMetrics(demo ? mockMetricsData : null);
} else {
  setMetrics(data); // <-- server mock data flows through here
}
```

The fix is either:
- Make the API route respect `NEXT_PUBLIC_DEMO_MODE` (unify the variables), or
- Have the client tag API responses with a `"source": "mock"` field that non-demo clients can reject, or
- Remove the server-side mock fallback and let the client handle demo display entirely (which this PR already does on the client side).

## Tradovate browser-side auth: CORS and endpoint mismatch

The settings page performs a direct browser fetch to `https://demo.tradovateapi.com/v1/auth/accesstokenrequest`. Two problems:

1. **CORS**: Tradovate's API is not typically configured to accept requests from arbitrary browser origins. This call will likely produce a CORS preflight failure, which the `catch` block interprets as "credentials saved, connection will be established later" — misleading the user into thinking their credentials are valid.

2. **Endpoint casing**: The adapter in `tradovate.ts` uses `accessTokenRequest` (camelCase T). The settings page uses `accesstokenrequest` (all lowercase). Tradovate's documentation shows camelCase. The lowercase variant may return 404.

The `handleTradovateConnect` error handler:

```typescript
} catch (error) {
  // Network errors are expected if there's no real API access
  // Still mark as connected for UX (credentials saved for later use)
  setPlatforms((prev) =>
    prev.map((p) =>
      p.id === "tradovate"
        ? { ...p, status: "connected" as const, lastSync: "Just now" }
        : p
    )
  );
  toast.success("Tradovate credentials saved...");
}
```

This fail-open behavior means the user can never distinguish between "bad credentials" and "network unavailable." The platform shows green checkmark regardless.

## Missing trades fetch path

`TradesPageContent` in production mode runs:

```typescript
useEffect(() => {
  if (demo) return;
  // In production, trades would come from the API
  // For now, we simply show empty state
  setLoading(false);
}, [demo]);
```

Similarly, `DashboardOverview` initializes `recentTrades` as `[]` in production mode and never fetches. The `Trade` model exists in Prisma, and there's even an API route structure for it, but no endpoint is actually called. Users in production mode will always see "No trades recorded yet" regardless of database state.

## Finances page lacks API persistence

`FinancesPageContent` persists transactions to `localStorage` only. In production mode (`isDemoMode() === false`), the initial state is `[]` unless `localStorage` has data. There is no `/api/finances` endpoint, no server-side storage. This is effectively browser-local data that vanishes on clearing site data or switching browsers.

## Dual environment variable confusion

The `.env.example` now has:
```
DEMO_MODE=true
NEXT_PUBLIC_DEMO_MODE=true
```

Both default to `true`. The middleware, auth, and API routes read `DEMO_MODE`. Client components read `NEXT_PUBLIC_DEMO_MODE`. The user's report ("I set DEMO_MODE to false and still see fake data") suggests they toggled the wrong one — or toggled one and not the other. A single `NEXT_PUBLIC_DEMO_MODE` variable (readable on both server and client in Next.js) would eliminate this class of misconfiguration, or alternatively the server routes should check the same variable the client does.
