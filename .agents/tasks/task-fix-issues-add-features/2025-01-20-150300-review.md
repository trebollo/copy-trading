# Demo login fix, dark mode, toasts, trades page, session metrics, and member table redesign (v2)

Three features ship together: fixing demo-mode authentication and adding UX infrastructure (dark mode via next-themes, sonner toasts), building a dedicated /trades page with pagination/filtering/sorting, enhancing metrics with profit factor and win rate time-series charts plus session breakdowns, and redesigning the group member list from cards to compact table rows with inline editing. The v1 review raised five issues; four have been fixed (Toaster moved inside ThemeProvider, Google login now shows fallback messaging, profit factor/win rate charts use deterministic data, dead `handleFilterChange` removed).

Watch for:
- **Trades page mock data still uses Math.random()** — entry prices, quantities, PnL, and minutes are generated with `Math.random()` in `generateMockTrades()`, so the trades table shows different data on every mount. (confirmed)
- **No test coverage for any new component** — still zero tests for trades-page, member-table, session-metrics, chart components, or toast integrations. (confirmed)
- **Member table row state doesn't sync with prop updates** — `MemberTableRow` copies `member.riskMultiplier` etc. into local state on mount but never re-syncs if props change. (confirmed)

## High-level view

The trades page generates 60 mock trades using `Math.random()` at module scope, so values differ per HMR cycle and per fresh page load. The instability was fixed for profit factor and win rate charts (now hardcoded arrays) but the same pattern was not applied to the trades mock generator.

The member table compresses each account into a single row with inline edit toggling. The row component copies risk parameters into local state on initial render; if the parent passes updated props after a save, the editing inputs pre-fill with stale mount-time values until the component remounts.

No tests were added for any of the new code. The existing 146 tests all pass but cover none of the six new components.

## Trades page mock data instability

The `generateMockTrades()` function in `trades-page.tsx` runs at module scope (outside the component), producing 60 trades using `Math.random()` for entry price, PnL, quantity, and the minute component of timestamps:

```tsx
entryPrice = 5200 + Math.random() * 100;
const pnl = status === "closed"
  ? Math.round((Math.random() * 1200 - 400) * 100) / 100
  : null;
quantity: Math.floor(Math.random() * 5) + 1,
```

Because it executes at import time, values differ on every HMR cycle and on every fresh page load. The v1 review flagged this pattern for the metrics charts and it was fixed there with hardcoded value arrays; the same fix should be applied here for consistency and to enable snapshot/visual testing.

## Member table row stale-state pattern

`MemberTableRow` initializes editing state from props:

```tsx
const [riskMultiplier, setRiskMultiplier] = useState(member.riskMultiplier);
const [maxLots, setMaxLots] = useState(member.maxLots);
const [maxDailyLoss, setMaxDailyLoss] = useState(member.maxDailyLoss);
```

The cancel handler resets to `member.*` (the current prop), which works correctly. But after `handleSave` updates the parent's `members` array and new props flow down, the local editing state still holds the values from mount time. If a user saves, then immediately clicks edit again, the inputs pre-fill with the old values rather than the freshly-saved ones. Adding a `key={member.id + member.riskMultiplier + ...}` on the row or a `useEffect` to sync would eliminate this.
