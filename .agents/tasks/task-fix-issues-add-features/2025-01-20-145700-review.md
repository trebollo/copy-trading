# Demo login fix, dark mode, toasts, trades page, session metrics, and member table redesign

Three features shipped together: fixing broken demo-mode authentication and adding UX infrastructure (dark mode, toasts), building a full trades list page with pagination/filtering, enhancing the metrics dashboard with profit factor and win rate time-series charts plus session breakdowns, and redesigning the group member layout from cards to a compact table.

Watch for:
- **Toaster rendered outside ThemeProvider** — the `<Toaster>` in `providers.tsx` sits as a sibling to `ThemeProvider`, not inside it. Toast popups won't follow the dark/light theme. (confirmed)
- **No test coverage for any of the three features** — 146 tests pass, but none cover new components (trades-page, member-table, session-metrics, profit-factor-chart, win-rate-chart, or the toast integrations). (confirmed)
- **Google login remains broken** — the user reported "no me funciona el login con Google" but the only fix addresses demo mode login. The Google provider depends on `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` env vars being set; nothing in this diff validates or surfaces that failure. (confirmed)

## High-level view

The demo login was broken because the landing page navigated directly to `/dashboard` without authenticating. The fix correctly routes through `signIn("demo")`, which hits the `CredentialsProvider` registered under `id: "demo"`. However, Google login — the other complaint — remains unaddressed; the provider silently fails when env vars are empty.

Dark mode is wired through `next-themes` with the correct plumbing (`suppressHydrationWarning`, `attribute="class"`, `useTheme()` in settings), but the `<Toaster>` component from sonner sits outside the `ThemeProvider` subtree, so toasts won't follow the theme.

The trades page is a self-contained client component backed by 60 hardcoded mock trades with filtering, column sorting, and pagination. Metrics gained profit factor and win rate time-series charts plus a "Sessions" tab, all backed by random mock data that regenerates on every mount — values aren't stable across navigations.

The member table redesign replaces card-per-member with a compact `<table>` where each row has an inline edit mode for risk parameters and an immediate active/inactive toggle.

## Demo login via signIn("demo") and the Google gap

The landing page previously did `router.push("/dashboard")` which bypassed authentication entirely — the session would be null on the dashboard. The fix calls `signIn("demo", { callbackUrl: "/dashboard" })` which invokes the `CredentialsProvider` with id "demo" registered in `src/lib/auth.ts` when `DEMO_MODE=true`.

The login page adds a conditional demo button gated on `process.env.NEXT_PUBLIC_DEMO_MODE === "true"`. Since this is a `"use client"` component, the env var is inlined at build time by Next.js — the gating works but requires a rebuild if the env var changes.

The user's complaint about Google login ("no me funciona el login con Google") is not addressed. The `GoogleProvider` requires `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`; when these are empty strings (the `?? ""` fallback), NextAuth registers the provider but OAuth will fail at runtime. There's no user-facing indication that Google auth is misconfigured — the button exists, fires `signIn("google")`, and the flow fails silently or redirects to an error page.

## Toaster outside theme context

In `providers.tsx`:

```tsx
<SessionProvider>
  <ThemeProvider attribute="class" defaultTheme="system" enableSystem>
    <QueryClientProvider client={queryClient}>
      {children}
    </QueryClientProvider>
  </ThemeProvider>
  <Toaster richColors />
</SessionProvider>
```

The `<Toaster>` sits as a sibling to `ThemeProvider`, not a child. Sonner's `<Toaster>` component defaults to `"light"` theme unless it receives theme context or an explicit `theme` prop. Since it's outside the next-themes context tree, toasts will always render in light mode regardless of the active theme. Fix: move `<Toaster>` inside the `ThemeProvider` subtree, or pass `theme={theme}` explicitly using a wrapper that calls `useTheme()`.

## Mock data instability in metrics charts

`SessionMetrics` uses hardcoded static data — stable across mounts. The profit factor and win rate charts in `metrics-dashboard.tsx` generate data inside `useMemo(() => { ... }, [])` using `Math.random()`. Because the memo runs once per mount and produces different values each time, the charts show different curves every time the user navigates away and back. This prevents meaningful visual testing or side-by-side comparisons.

## Member table — stale local state on external updates

The `MemberTableRow` initializes local state from props (`useState(member.riskMultiplier)`) but doesn't re-sync if props change externally. If another mechanism updates the member data (websocket, parent re-fetch), the row's edit state will be stale until the user reloads the page. For a demo app with no real-time updates this is low risk, but the pattern won't scale to production without a `useEffect` sync or key-based remounting.
